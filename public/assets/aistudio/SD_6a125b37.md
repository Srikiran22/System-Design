# System Design Repository — Engineering Best Practices & Improvement Plan

**Prepared:** 27 November 2026  
**Scope:** Source-informed review of `System-Design-main`, plus external engineering research for security, frontend, backend, database, full-stack architecture, testing, DevSecOps, reliability, accessibility, documentation and learning-platform governance.  
**Purpose:** Turn the current repository into a stronger, verifiable engineering learning product and use it as a practical full-stack engineering curriculum.

> This is an engineering review and improvement plan, not a penetration test, formal compliance assessment, production configuration audit, or claim that every external recommendation is already implemented.

---

## 1. Executive recommendation

The highest-value next step is **not** to add microservices, more frameworks, or a large set of new features. First make the existing modular application trustworthy end to end: ensure learner evidence and snapshots really persist in production; prove account isolation at both the server-function and PostgreSQL RLS layers; automate the security and quality checks; then establish observability, release controls and accessibility/performance budgets.

The project already has several good foundations: strict TypeScript settings, Zod request validation, server-side authentication checks, owner-scoped account queries, explicit CSRF middleware, a local progress outbox with retries, source provenance metadata and automated content-pack validation. Those are worth preserving.

The most serious repo-observed defect is in the progress-sync contract. The production `recordEvents` branch persists progress events but reports `syncedEvidence: 0` and does not persist the supplied learner evidence or snapshot. The client `ProgressSync` component nevertheless acknowledges the evidence batch and snapshot after a successful function response. The production snapshot read returns an empty snapshot, and production dossier export returns no evidence. **This can discard locally queued evidence while presenting the sync as successful.** Treat it as a P0 data-integrity issue, ahead of cosmetic work.

### Recommended order

1. Correct the evidence/snapshot persistence and acknowledgement contract.
2. Verify and test all authentication, authorization and RLS boundaries.
3. Establish a repeatable CI test and security gate.
4. Add operational visibility for sync, auth, database and frontend health.
5. Harden browser headers, rate limits, privacy and production configuration.
6. Improve accessibility, frontend state management and performance using measurable targets.
7. Expand advanced architecture topics only when the product demonstrates the need.

- TanStack Start and TanStack Router for the full-stack application and routing.

### 3.3 Confirmed high-priority issue: progress sync can lose evidence

**Relevant files:**

- `src/lib/neet/account.functions.ts` — `recordEvents` around lines 246–296; `getLearnerSnapshotFn` around 298–323; `exportDossier` around 325 onward.
- `src/components/neet/ProgressSync.tsx` — payload submission and acknowledgement around lines 117–176.

**Observed behavior:**

1. The client sends progress events, evidence and optionally a snapshot.
2. The production server path writes progress events only.
3. It returns success with `syncedEvidence: 0` and does not confirm snapshot persistence.
4. The client acknowledges/dequeues `evidenceBatch` and `snapshotAcked` after the success response, without checking accepted evidence/snapshot counts or durable snapshot status.
5. The production snapshot read returns `{ stateJson: null, updatedAt: null, evidence: [] }`.
6. The production dossier path exports profile/goals/events but an empty evidence list.

**Why it matters:** the client outbox is the durability buffer. Deleting an item before the server proves it has committed the item turns a retry mechanism into a data-loss mechanism. A successful HTTP/server-function response is not enough when the response explicitly says zero evidence synced.

**Required fix shape:**

- Define an explicit sync acknowledgement contract, e.g. `acceptedEventIds`, `acceptedEvidenceIds`, `snapshotVersion`, `serverTimestamp`, `rejectedItems[]`.
- Persist events, evidence and snapshot state transactionally or expose separate durable operations with separate acknowledgements.
- Make evidence idempotent using a stable client-generated idempotency key and a database unique constraint.
- Acknowledge only the exact IDs returned as durably committed. Do not acknowledge a snapshot merely because one was sent.
- If the production storage schema must change, follow `AGENTS.md`: have Lovable create/apply the schema changes; do not hand-edit protected migration files.
- Add tests that simulate partial success, duplicate retry, offline reconnect, snapshot conflict, user switch/logout and server failure after partial DB work.
- Ensure dossier export and cross-device hydration read the same canonical evidence records that sync writes.

**Acceptance criteria:** a test can enqueue one event, two evidence items and a snapshot; force a network retry and duplicate delivery; then prove exactly one durable copy exists for each idempotent item, no item is removed from the outbox before durable acknowledgement, and a second device can hydrate the saved snapshot/evidence.

## 4. Security engineering practices

Use the OWASP Top 10 as an awareness checklist and OWASP ASVS 5.0.0 as a verifiable engineering requirements source. For this learning platform, start with a practical subset of ASVS Level 1 controls, then add targeted Level 2 controls where learner identity, account evidence, private exports or administrative privileges create greater impact. Do not claim compliance without a documented scope, evidence and test results.

### 4.1 Threat model before implementation

For each feature, write down:

- **Assets:** learner profile, goals, progress events, evidence, snapshots, exports, source pack, AI gateway credentials, Supabase credentials, admin/editor functions.
- **Actors:** anonymous visitor, signed-in learner, another learner, content editor, administrator, automated sync client, third-party integration.
- **Trust boundaries:** browser ↔ server function; server ↔ Supabase Auth; server ↔ Postgres; browser local storage ↔ cloud sync; content ingestion ↔ canonical source pack; build pipeline ↔ production deployment.
- **Abuse cases:** change another user's ID, replay a sync request, submit duplicate or oversized evidence, mass-assign privileged fields, call a private server function directly, exploit a stale token, poison imported Markdown/source links, abuse exports or model calls, force expensive repeated operations.
- **Controls and tests:** choose preventive, detective and recovery controls; add a test for each important threat.

A short threat model can be a Markdown table in `docs/security/` or an ADR. Update it when a new data type, endpoint, role or external integration is introduced.

### 4.2 Authentication is not authorization

- Authentication proves who the requester is. Authorization determines which operation they may perform on which resource and which fields they may read or change.
- Every server function, route action or API endpoint that reads or mutates private data must perform its own auth check. A route guard, `beforeLoad`, hidden button or client-side role check is only user experience.
- Derive the effective user ID from verified claims/session context. Do not accept a client-supplied `userId`, `ownerId`, role or tenant ID as authority.
- Enforce object-level authorization on every record ID supplied by a client (prevent BOLA/IDOR). Also enforce property-level authorization: define editable DTOs explicitly instead of accepting arbitrary model objects.
- Use default-deny authorization. Add explicit role/action/resource rules for any editor/admin capability, and log important denied or privileged actions without exposing secrets.
- On password/role change or session privilege changes, ensure session lifecycle and token refresh/revocation follow the identity provider's supported model.

### 4.3 Supabase/Postgres authorization and RLS

For every table exposed through the Data API:

1. Confirm the intended schema exposure and table grants.
2. Enable RLS on every exposed table that should not be public. RLS policies do not automatically remove table grants; grants and policies must both be correct.
3. Write explicit policies for `SELECT`, `INSERT`, `UPDATE` and `DELETE` as relevant. `USING` and `WITH CHECK` serve different purposes; test each operation.
4. Scope policies to verified identity/claims, typically `auth.uid()` or a deliberate, verified role claim.
5. Test cross-user cases: user A must not read/update/delete user B's profile, goal, progress, evidence or snapshot.
6. Test the anonymous role, authenticated user, elevated admin/service role and any server-side job role separately.
7. Keep `service_role`/secret keys server-side only. It bypasses RLS; code using it must perform explicit authorization and should be rare and narrowly scoped.
8. If using views over protected tables, verify invoker/definer security behavior and whether the view should use `security_invoker = true`.
9. Index policy predicate columns where query plans show benefit, and inspect actual plans rather than indexing every field.
10. Add pgTAP tests and application-level tests through the same Supabase client path used by the app.

**Required policy test matrix:** anonymous user; authenticated owner; authenticated non-owner; user with another role; deleted/disabled account; row with null/malformed ownership; record ID not found; update attempting to change `user_id`; update attempting to modify a protected field. Assert both allowed and denied outcomes.

### 4.4 Session, cookies and tokens

- Use the supported Supabase SSR/browser client patterns for the exact TanStack Start version. Do not invent a parallel token format if the managed auth flow already covers the use case.
- On the server, validate claims/signature (`getClaims`) or fetch a fresh Auth user record (`getUser`) based on the operation. Do not make authorization decisions from an unverified `getSession()` user object that originated in client-controlled storage.
- Keep access/refresh tokens and session cookies out of URLs, logs, analytics events, screenshots and exception messages.
- Where the application controls session cookies, use `HttpOnly`, `Secure` on HTTPS, a deliberate `SameSite` policy, bounded lifetime and a safe host/path scope. Keep cookie refresh and response headers correct in SSR.
- Do not cache personalized HTML or refreshed auth-cookie responses in a shared CDN cache. Use private/no-store semantics for account data unless a correct user-specific cache design is proven.
- Test logout, expiration, refresh, password reset, token tampering, replay and multi-tab behavior.

### 4.5 CSRF, CORS and browser boundaries

- Preserve the explicit `createCsrfMiddleware()` currently in `src/start.ts`; custom Start configuration can require re-adding it.
- Keep browser server-function calls same-origin unless there is a clear cross-origin integration requirement.
- If a public cross-origin API is required, use a narrow explicit origin allowlist. Do not combine credentialed requests with wildcard origins.
- Validate allowed methods and headers. Treat CORS as a browser access policy, not authentication or authorization.
- Do not disable origin checks merely to make a test or proxy work; first identify which proxy/header behavior is changing.
- Test preflight and mutating requests against the production build and real hosting path.

### 4.6 XSS, CSP and content rendering

- Render text as text. Do not pass untrusted strings into `dangerouslySetInnerHTML`.
- For Markdown content, verify raw HTML is disabled or sanitized, link protocols are allowlisted (`https`, `http`, `mailto` only where needed), and external links use safe target behavior.
- Add a Content Security Policy only after inventorying legitimate script, style, font, image, connection and frame sources. Start with `Content-Security-Policy-Report-Only`, collect violations, then enforce. Prefer nonces/hashes for scripts; avoid broad `unsafe-inline` where possible.
- Use `object-src 'none'`, a deliberate `base-uri`, and `frame-ancestors` policy where compatible. Decide whether framing is required before using `X-Frame-Options: SAMEORIGIN` or `DENY`.
- Confirm HSTS at the TLS termination layer for production HTTPS; use `includeSubDomains`/preload only when all relevant subdomains are HTTPS-ready.
- Keep `X-Content-Type-Options: nosniff`, a suitable Referrer-Policy and Permissions-Policy; verify headers on deployed pages and API responses, not just in source code.

### 4.7 Validation, injection and untrusted content

- Validate all server inputs with Zod or an equivalent runtime schema. TypeScript types disappear at runtime and are not validation.
- Validate syntax and semantics: IDs, enum values, string length, arrays, date ranges, relationship ownership, quotas, state transitions and evidence formats.
- Use parameterized queries and safe query builders; never concatenate user input into SQL, shell commands or dynamic file paths.
- Encode output for its context (HTML, URL, CSS, JavaScript, Markdown, log fields). Avoid “sanitize once, safe everywhere” assumptions.
- Treat imported sources, external API payloads, Markdown, filenames and queued browser data as untrusted even when they come from a trusted upstream integration.
- Apply file size/type/content limits if file uploads are added. Store uploads outside executable paths and apply authorization to every retrieval.

### 4.8 SSRF and outbound requests

If the application ever fetches a URL supplied by a user or a content record (source previews, link checker, remote image import, webhook testing):

- Allowlist schemes and, where possible, hostnames.
- Resolve DNS and block loopback, private, link-local and metadata-service IP ranges for IPv4 and IPv6.
- Re-check redirects and DNS results at every hop; an allowlisted hostname can redirect to a forbidden IP.
- Set timeouts, response-size limits, content-type restrictions and concurrency quotas.
- Never forward user cookies or internal credentials to the fetched destination.
- Prefer a controlled fetch worker with constrained egress over adding arbitrary URL-fetching to a request handler.

### 4.9 Abuse prevention and rate limits

Rate limit by both identity and network signals where appropriate. Different operations need different limits:

- Login, password reset, verification, account creation and token refresh: credential-attack protection, generic errors, bot detection/CAPTCHA where risk warrants it.
- Progress/evidence writes: per-user request and item quotas, maximum batch sizes, idempotency and anomaly detection.
- Search/exports/AI gateway: per-user concurrency, daily budget and response-size limits.
- Public discovery/content endpoints: IP-based limits and CDN caching where safe.

Do not rely on an in-memory limiter in a horizontally scaled production deployment unless the limitation is intentional. Use the hosting provider, gateway or shared store. Return appropriate `429` responses and `Retry-After` where applicable. Make clients back off with jitter and do not retry permanent validation/auth failures.

### 4.10 Secrets, privacy and security logging

- Keep environment secrets in the managed deployment secret store. Never commit `.env`, private tokens, database passwords, service-role keys or AI gateway credentials.
- Use least-privilege keys and rotate exposed credentials immediately.
- Do not log tokens, passwords, session IDs, raw request cookies, full learner evidence or sensitive personal details.
- Use structured logs with timestamp, severity, route/operation, result, duration, request/correlation ID and a safe user reference. Redact or hash identifiers where appropriate.
- Make privileged changes, repeated authorization denials, suspicious sync replay, repeated login failures and anomalous export activity auditable.
- Define log retention and access; logs themselves can contain personal data.

### 4.11 Software supply-chain security

- Pin GitHub Actions to full commit SHAs, not floating tags, when using GitHub Actions.
- Grant CI only the minimal `GITHUB_TOKEN` permissions required by each job.
- Enable secret scanning and push protection where available; scan repository history if a secret may have been committed.
- Run dependency vulnerability checks on pull requests and scheduled runs; separate direct and transitive dependencies.
- Generate an SBOM (SPDX or CycloneDX) for release artifacts.
- Add provenance for build artifacts as the pipeline matures; use SLSA guidance rather than claiming a level that has not been achieved.
- Protect release branches, require code review and checks, and restrict workflow changes.

## 5. Frontend engineering practices

### 5.1 Component architecture

- Organize code around product/domain features, not only generic technical folders. A lesson, learner profile, progress sync and evidence flow should have clear ownership and public interfaces.
- Keep reusable UI components generic and presentation-focused; keep domain decisions in feature/application modules.
- Avoid one component owning routing, networking, state orchestration, validation, analytics and display at once.
- Prefer composition and small focused components over a universal component with many booleans and branches.
- Preserve Radix primitives for complex keyboard/focus behavior; wrap them with project design tokens and consistent variants rather than rebuilding accessible primitives from scratch.
- Do not create abstractions for a single trivial use case unless they clarify an important boundary.

### 5.2 State ownership and data flow

Choose the state owner deliberately:

| State kind | Appropriate owner | Example in this project |
|---|---|---|
| Server state | TanStack Query or route loader/server function | Account profile, progress events, library data |
| Ephemeral UI state | Component state | Open dialog, active tab, selected filter |
| Navigational/shareable state | URL/search params | Current path, lesson, filter, sort or search term |
| Durable local/offline state | Explicit store + outbox | Locally created progress events and evidence awaiting sync |
| Derived state | Compute from canonical state | Completion percentage, radar chart score, progress summary |

Avoid storing the same fact in multiple places unless you have a documented synchronization rule. Do not store values that can be derived cheaply; redundant state creates contradictory UI.

For the progress platform, distinguish at least: **local-only**, **pending sync**, **server accepted**, **rejected**, and **conflicted**. Do not display “synced” based only on a successful request when individual record types were not persisted.

### 5.3 React effects and lifecycle

- Use render-time calculations for derived values; use event handlers for user-triggered changes.
- Use effects for synchronization with external systems: subscriptions, browser APIs, timers, external widgets or imperative libraries.
- Every subscription/timer/event listener should have cleanup; make setup/cleanup safe to repeat.
- Use abort signals or request identity guards to prevent stale async results overwriting current state.
- Keep Strict Mode enabled in development to surface missing cleanup and impure rendering.
- Prefer framework loaders/TanStack Query for data fetching and cache lifecycle rather than hand-rolled effects for routine server state.

### 5.4 Loading, errors, empty and offline states

For each user journey, design and test:

- Initial loading and delayed loading.
- Empty first-use state vs genuinely empty search result.
- Validation error next to the relevant control.
- Server failure with retry where retry is safe.
- Expired session and re-authentication.
- Offline state and pending local changes.
- Partial sync, rejected record and conflict resolution.
- Success state with a verifiable confirmation.

A toast should not be the only place a critical error appears. Preserve user input after transient failures. Avoid optimistic UI for irreversible/high-impact operations unless you have rollback semantics.

### 5.5 Forms and validation

- Use semantic labels, native controls where possible, required/optional cues, clear format guidance and inline errors.
- Share schemas or rule definitions where practical, but validate again on the server. A client schema is for feedback, not security.
- Return field-level errors in a predictable shape and associate them via `aria-describedby`.
- Prevent double submit and explain pending state.
- For sensitive actions, confirm the actual effect and provide a safe undo/recovery path when possible.

### 5.6 Accessibility: use WCAG 2.2 AA as the working target

Accessibility must be built into component acceptance criteria, not treated as a late visual audit.

- Semantic HTML first; correct heading order and landmarks.
- Full keyboard access; no keyboard traps; visible focus indicator; focus is not obscured by sticky navigation/dialogs.
- Every input has a programmatic label; buttons have meaningful accessible names; icons are decorative or properly labelled.
- Dialogs manage focus, announce title/description, close predictably and restore focus.
- Provide text alternatives for charts and visual status; do not communicate status using color alone.
- Meet contrast requirements; support zoom/reflow and narrow screens without losing content or function.
- Respect reduced-motion preferences and avoid unnecessary animation.
- Make touch targets large enough, especially for primary controls; check WCAG 2.2 target-size criteria.
- Use automated axe checks for broad coverage, then manual keyboard and screen-reader review for actual user flows. Automated checks alone do not prove WCAG conformance.

### 5.7 Frontend performance

Set real-user performance goals at the 75th percentile:

| Metric | Good target |
|---|---:|
| Largest Contentful Paint (LCP) | ≤ 2.5 s |
| Interaction to Next Paint (INP) | ≤ 200 ms |
| Cumulative Layout Shift (CLS) | ≤ 0.1 |

Practical measures:

- Establish route-level bundle budgets and inspect bundle changes in pull requests.
- Lazy-load noncritical routes, charts and heavy editors; avoid shipping an entire visualization library to routes that do not use it.
- Reserve image dimensions and use responsive formats/sizes to reduce layout shifts.
- Preload only genuinely critical fonts/assets; avoid excessive font weights and large icon packs.
- Keep long tasks off the main thread; virtualize large tables/lists if measurement shows a need.
- Use TanStack Query caching intentionally: stale time, invalidation and refetch behavior should match the data's freshness requirements.
- Avoid caching private account data in shared CDN/SSR caches.
- Measure with production-like builds and real devices, not only a local dev server.

### 5.8 Frontend security and content integrity

- Treat every string from a remote content source as untrusted display data.
- Audit Markdown rendering, external links, URL parsing and SVG/image handling.
- Do not expose secrets in Vite variables or code reachable from the browser.
- Avoid writing sensitive learner data to browser storage unless the design requires offline use; document retention, logout cleanup and account-switch behavior.
- Ensure local progress and outbox data are namespaced by authenticated account and purged or isolated on logout/account switch.

## 6. Backend and API engineering practices

### 6.1 Server functions are API boundaries

TanStack Start server functions are callable endpoints, not private helper calls. For every server function:

1. Use the correct HTTP method; reads should not mutate.
2. Validate runtime input with Zod.
3. Authenticate where required.
4. Authorize the action/resource/field for the current principal.
5. Enforce business invariants and quotas.
6. Execute DB work transactionally where multiple writes represent one operation.
7. Return a narrow DTO, not a raw database row with internal fields.
8. Emit safe logs/metrics and stable error responses.
9. Add tests for anonymous, owner, non-owner, invalid and adversarial inputs.

Organize code so `*.functions.ts` files expose validated server-function wrappers, `*.server.ts` files contain server-only database and secret access, and shared schema/types stay client-safe. The exact pattern should follow the TanStack version and existing repo structure, not be copied blindly.

### 6.2 API contracts and errors

- Define stable response shapes for success, validation errors, unauthenticated, forbidden, not found, conflict, rate limited and unexpected failure.
- Use machine-readable error codes; do not make frontend logic parse human-readable messages.
- Avoid exposing stack traces, SQL details, internal paths, environment names or secrets to clients.
- Return only the fields the caller needs. Use explicit DTOs to avoid accidental property exposure and mass assignment.
- Add a correlation/request ID so a user-visible failure can be traced safely in logs.
- Document important server-function contracts; for externally consumed APIs, use an OpenAPI/contract description or a similarly explicit schema.

### 6.3 Idempotency and transaction boundaries

This is especially important for the outbox:

- Generate stable idempotency keys on the client before first submission; retrying the same logical event must reuse the key.
- Put a unique constraint in the database on the proper owner + idempotency key combination.
- Upsert/insert with a clear conflict policy; do not rely on the UI preventing duplicate requests.
- Acknowledge an item only after the transaction commits.
- If an operation writes progress event + evidence + snapshot, decide whether these are one atomic unit or multiple independently acknowledged resources. Make that decision explicit in the contract.
- Use optimistic concurrency/version checks for snapshots to prevent an old device overwriting newer state.
- Test lost response after commit: client retries, server returns the already-committed result without duplication.

### 6.4 Pagination and bounded data access

- Do not fetch unbounded learner history, source lists or evidence collections.
- Use cursor/keyset pagination for growing datasets; provide deterministic order and opaque cursors.
- Define maximum page/batch sizes and response bytes.
- Avoid `select *` in API responses; retrieve only needed columns.
- Add indexes based on common access patterns and `EXPLAIN (ANALYZE, BUFFERS)` in a representative staging dataset.
- Ensure pagination predicates match index order; document tie-breakers for stable paging.

### 6.5 Caching

- Cache public static course/content assets aggressively with versioned URLs when safe.
- Treat account profiles, learner evidence and exports as private data.
- Explicitly choose cache headers per endpoint/route. Do not rely on framework defaults for personalized responses.
- Invalidate TanStack Query caches when a mutation changes their source records.
- Never allow a shared cache to serve one user's response to another user.
- Measure cache hit rate and stale-data complaints before adding complex cache layers.

### 6.6 Resilience and external integrations

- Give outbound requests explicit connection/read timeouts and response size limits.
- Retry only transient failures (network errors, selected 5xx, 429 with `Retry-After`); do not retry auth/validation/permission errors.
- Use exponential backoff with jitter and a maximum retry window.
- Bound concurrent work and queue length; apply backpressure rather than allowing unlimited promises or jobs.
- Use idempotency for retried writes.
- For repeatedly failing external dependencies, consider a circuit breaker and fallback, but only when it is justified by the failure mode.
- Record dead-letter/rejected work and provide a controlled reprocessing path.

### 6.7 Background work

Keep request handlers short. Move long content processing, link checking, exports or batch recalculation into background jobs when measured duration/volume justifies it. Background jobs need:

- A durable queue or job record.
- Idempotent workers.
- Retry and dead-letter policy.
- Per-job timeout and resource limits.
- Progress state and user-facing result semantics.
- Trace/correlation ID from initiating request to job completion.

Do not add a queue service for small synchronous work that does not need one.

## 7. Database and data engineering practices

### 7.1 Put invariants in the database too

Validation in TypeScript is necessary but not enough. Where the schema supports it, use:

- `NOT NULL` for required fields.
- Foreign keys for ownership/relationship integrity.
- Unique constraints for idempotency and canonical identity.
- Check constraints for bounded values and valid status fields.
- Appropriate enums/reference tables for finite state values.
- Transactions for related writes.

A database constraint prevents invalid states from alternate code paths, scripts and future services.

### 7.2 SQLite and PostgreSQL parity

The local SQLite path is useful for fast tests, but it is not identical to PostgreSQL or Supabase. Differences can appear in SQL behavior, data types, concurrency, constraint enforcement, RLS, auth claims, transaction behavior and query planning.

Recommended test split:

- Fast unit tests using isolated SQLite/in-memory logic where appropriate.
- Integration tests against a local Supabase/PostgreSQL environment for SQL-specific and RLS behavior.
- End-to-end tests through the same Supabase client and server functions used by the application.
- A staging smoke test after schema changes and before production rollout.

Do not claim PostgreSQL/RLS correctness based only on SQLite unit tests.

### 7.3 Schema change workflow

Use an expand–migrate–contract approach for live data:

1. Add backward-compatible nullable/new structures.
2. Deploy application code that can read old and new structures.
3. Backfill data in bounded, observable batches.
4. Verify counts, constraints and query behavior.
5. Switch reads/writes.
6. Remove obsolete structures only after no running release needs them.

Define a rollback/recovery plan for each production schema change. Respect the repository's Lovable-managed migration boundary; the engineering principle still applies, but the migration must be authored/applied via the approved project workflow.

### 7.4 Backups and recovery

- Know what is backed up, how often, and for how long.
- Define recovery point objective (RPO) and recovery time objective (RTO) in terms the product actually needs.
- Perform restore drills; a backup that has never been restored is an assumption, not verified recovery capability.
- Protect exported snapshots and evidence with the same access controls as their source records.
- Test account deletion and data-retention workflows against backups and downstream exports.

## 8. Full-stack architecture and maintainability

### 8.1 Prefer a modular monolith now

The current project does not show a requirement for independently deployed services. A modular monolith gives simpler local development, transactions, deployment, observability and auth boundaries.

Use modules around business capabilities (content/library, learning paths, progress, evidence/competencies, account/auth, sync, analytics) with explicit interfaces. Extract a service only when there is a measurable need such as independent scaling, team ownership, different runtime, separate security boundary or release cadence.

### 8.2 Keep trust boundaries visible in code

- Browser-safe modules must not import secrets, server DB clients or server-only SDKs.
- Server-only modules own the database connection and sensitive configuration.
- Shared modules contain schemas, types, constants and pure calculations only.
- Generated files are clearly labelled and never edited by hand.
- Every feature's data access flows through one deliberate contract; avoid duplicate helpers that disagree about auth or ownership.

### 8.3 Establish architecture decision records (ADRs)

Record consequential decisions in `docs/adr/` using a small template:

- Context and problem.
- Constraints and options considered.
- Decision and why it was chosen.
- Security, reliability, cost and maintenance consequences.
- Revisit conditions (what evidence would make the team change the decision).

Good ADR subjects for this repository: local vs cloud data ownership, learner evidence durability, service-role usage, auth source of truth, content pack import, caching boundaries and the decision to stay modular-monolith.

### 8.4 Avoid premature complexity

Do not add microservices, Kafka, Kubernetes, GraphQL, Redis, event sourcing or a generic plugin architecture just because they appear in system-design curricula. Learn the concepts in isolated labs, then use them in the real app only when requirements justify the operational cost.

## 9. Testing and quality engineering

### 9.1 Test layers

| Test level | Main purpose | High-value examples for this repo |
|---|---|---|
| Static analysis | Catch type/lint defects early | `tsc --noEmit`, ESLint, Prettier check |
| Unit | Pure logic and invariants | Progress math, rubric scoring, competency derivation, token validation, outbox merge/backoff |
| Component | Interaction and rendering | Lesson actions, forms, dialogs, status and offline indicators |
| Integration | Server function + DB behavior | Account CRUD, event/evidence persistence, snapshot hydration, export and error contracts |
| Database/RLS | Prove policy behavior | pgTAP tests as anon/user A/user B/admin; include positive and negative cases |
| Browser E2E | Test full user journeys | Sign in, learn lesson, create evidence, go offline, reconnect, sync, reload on another device/session, export dossier |
| Accessibility | Catch assistive-tech barriers | axe checks + manual keyboard, focus, zoom and screen-reader pass |
| Security regression | Prevent known bug reintroduction | BOLA/IDOR, mass assignment, CSRF, XSS, session expiry, rate-limit and injection cases |
| Resilience | Exercise failure behavior | Network loss, 429, 500, partial DB failure, duplicated event, stale snapshot, DB unavailable |

### 9.2 Test important negative cases

For every authorization boundary, test both what should work and what must fail. Particularly:

- User A cannot read or mutate User B's record by changing an ID.
- A signed-in user cannot set their own role, ownership, billing or verification fields.
- A server function called directly cannot bypass a route-level guard.
- A stale/revoked/expired token is rejected.
- A duplicate sync retry does not duplicate an event or evidence item.
- A server response that only accepted events does not cause evidence/snapshot to be acknowledged.
- An invalid or oversized batch is rejected before resource-intensive work.
- An offline user sees pending data as pending, not synced.

### 9.3 CI pipeline recommendations

The checked repository tree did not contain a GitHub Actions workflow. A first useful pipeline should be small and deterministic:

1. Install from lockfile with a pinned supported Node version.
2. Run formatting check and lint.
3. Run TypeScript typecheck.
4. Run Vitest.
5. Run knowledge-pack validation and source-index consistency checks.
6. Build production bundle.
7. Run dependency/secret scanning.
8. Run DB/RLS tests against a local test database when those tests are introduced.
9. Publish test/build artifacts and summaries.

Make all required jobs branch-protection checks. Use least-privilege job permissions, full-SHA action pins and no production secrets in untrusted pull-request workflows.

### 9.4 Test quality over coverage vanity

Line coverage is useful as a signal, not as the objective. Track whether the tests exercise important business invariants, negative authorization paths, failure/retry states and real browser journeys. A 90% line-coverage number can still miss a single user-to-user data leak.

## 10. DevSecOps, deployment and release management

### 10.1 Environments

Use separate development, staging and production environments with distinct database projects, credentials and user datasets. Staging should resemble production closely enough to test SSR, auth cookies, RLS, CDN behavior, migrations, rate limits and observability.

### 10.2 Build once, promote the same artifact

- Build a commit once and promote that same artifact between staging and production.
- Keep environment-specific secrets/config outside the artifact.
- Record commit, dependency lockfile, build ID and deployment identity.
- Verify build provenance/SBOM for production releases as the pipeline matures.

### 10.3 Release safety

- Use small pull requests with a problem statement, risk analysis, tests, screenshots where useful and migration notes.
- Require at least one meaningful review for sensitive auth/data/infra changes.
- Use feature flags to control gradual exposure, not to hide incomplete security checks.
- Deploy low-risk changes progressively and monitor key metrics.
- Keep rollback procedures documented and tested.
- Schema changes must remain backward-compatible during rolling deployment.
- Have a defined hotfix path that still preserves auditability and does not rewrite published history.

### 10.4 Production readiness checks

Before real learner data is relied on, verify from the actual cloud project and deployment:

- RLS enabled and grants/policies reviewed for every exposed table.
- SSL enforcement and network access restrictions configured where supported/appropriate.
- Auth email/OTP/SMTP settings, MFA policy, CAPTCHA/bot protection and rate limits reviewed.
- Service-role and other secrets are server-side and rotated appropriately.
- CDN and SSR cache behavior is safe for private routes/cookies.
- Security headers (including CSP/HSTS where applicable) verified on the actual deployed response.
- Backups enabled, retention known and restore drill completed.
- Error reporting, logs, metrics and alerts are functional.
- Query/index performance tested with representative data and expected concurrency.
- Incident owner and support/escalation route known.

## 11. Reliability and operations

### 11.1 Define a small set of user-facing SLIs/SLOs

Do not begin with dozens of dashboards. Start from user outcomes:

| User capability | Useful SLI | Example objective to discuss |
|---|---|---|
| Authentication | Successful valid sign-in rate; sign-in latency | Set an objective based on expected availability and auth provider dependency. |
| Learning content | Successful content load; LCP | Content should load quickly and predictably on normal mobile networks. |
| Progress sync | Durable sync success rate; oldest pending outbox age | No data loss; pending evidence eventually reaches the server or remains clearly pending. |
| Account data | Successful profile/goal/evidence read/write rate | Owner data is available without cross-user leakage. |
| Export | Successful dossier creation; export latency | Export reports completion only after evidence is included or clearly explains partial state. |

Treat numeric SLO targets as a product decision, not invented guarantees. Start by measuring a baseline, then choose targets. An error budget can inform whether to slow risky releases after reliability degrades.

### 11.2 Observability signals

Adopt structured logs, metrics and traces; OpenTelemetry provides shared conventions and instrumentation patterns.

Prioritize these project-specific signals:

- Outbox pending item count and oldest pending age.
- Event/evidence/snapshot submission count, acceptance count and rejection count separately.
- Client outbox acknowledgements vs server durable-acceptance acknowledgements (should match by ID/type).
- Sync retry count, retry reason, time-to-sync and conflict count.
- Server-function latency and failure rate by operation.
- Authentication failure rate, token refresh errors and authorization denials.
- Supabase query latency, connection pool pressure and slow query counts.
- Frontend LCP/INP/CLS for key routes.
- Error volume and release-to-error correlation.

Do not use raw email, tokens, evidence text or other high-cardinality/sensitive fields as metric labels.

### 11.3 Alerting and incident response

- Alert on user-visible symptoms, not every internal error.
- Use SLO burn rates or a small set of actionable thresholds.
- Every alert needs an owner, a runbook and a clear action.
- Write runbooks for login outage, progress-sync backlog, Supabase/DB outage, content ingestion failure, bad release and data restore.
- Record incidents with timeline, impact, root/contributing factors and corrective actions. Keep reviews blameless and focused on system improvements.
- Test the recovery procedure after the fix; the incident is not closed merely because the page is healthy again.

### 11.4 Health checks and capacity

Separate liveness (process is alive) from readiness (can serve traffic safely). Avoid leaking secrets or internal infrastructure in public health responses. Load-test expected concurrency and burst patterns, especially progress sync and bulk reads. Monitor database connection usage and queue growth before adding more infrastructure.

## 12. Knowledge-pack, content and learning-platform governance

This repository is more than a generic CRUD app; the quality of its instructional content and evidence model is part of product correctness.

### 12.1 Preserve strong existing governance

`docs/CONTENT_GOVERNANCE.md` provides useful rules:

- `content/pack/` is canonical.
- Generated source-enrichment TypeScript is derived output.
- Explicit inline citations must remain distinct from topic-matched reading.
- Source records distinguish authority tier and extraction/provenance status.
- Paywalled standards are summarized with attribution; normative text is not copied wholesale.

Keep these principles. They reduce fabricated references, provenance ambiguity and licensing risk.

### 12.2 Add a content maintenance lifecycle

Each important source/lesson should have:

- Owner or review role.
- Canonical source URL and source ID.
- Authority tier and extraction status.
- Last-checked date and next review trigger.
- Version/edition information for standards and fast-changing documentation.
- Known limitations, partial extraction or licensing note.
- Lesson-to-competency mapping and expected learner evidence.

Automate link checks and stale-version reports, but do not automatically upgrade an official standard citation without reviewing the semantic differences.

### 12.3 Assessment and evidence quality

- Define rubrics with observable behaviors and evidence criteria.
- Include examples of strong, partial and insufficient evidence.
- Calibrate rubric scoring across reviewers or test cases.
- Preserve provenance for learner evidence: when it was created, which task/lesson it supports, the rubric version and whether it was locally queued or server-confirmed.
- Make export distinguish missing evidence from zero evidence and locally pending evidence from persisted evidence.
- Do not calculate competency confidence from events that have not been durably accepted or have ambiguous provenance.

## 15. Practical Definition of Done checklist

A feature is not done merely because the happy path works locally. Before considering a meaningful feature complete, ask:

### Product and design
- [ ] The user problem and non-goals are clear.
- [ ] Loading, empty, error, offline and success states are designed.
- [ ] Responsive behavior and accessibility have been considered.

### Frontend
- [ ] State has one deliberate owner; derived state is not duplicated unnecessarily.
- [ ] Forms and controls have accessible labels, keyboard behavior and useful errors.
- [ ] No private secret or server-only module is reachable from browser code.
- [ ] The UI does not claim remote persistence until the server confirms it.

### Backend and data
- [ ] Inputs are validated at runtime.
- [ ] Authentication and authorization are enforced in the server handler.
- [ ] Object and field-level access are checked.
- [ ] Related writes are transactional or independently acknowledged.
- [ ] Idempotency, concurrency, pagination and size limits are defined.
- [ ] Database constraints and RLS match business invariants.

### Testing and security
- [ ] Unit/integration tests cover main behavior and meaningful failure cases.
- [ ] Cross-user/unauthenticated/invalid-input tests exist for private data.
- [ ] Accessibility and browser journeys are covered at the appropriate risk level.
- [ ] Dependencies and secrets are checked through automation.

### Operations and release
- [ ] Logs/metrics make failures diagnosable without sensitive data.
- [ ] Cache behavior is appropriate for public vs private data.
- [ ] Deployment, rollback and schema-change order are understood.
- [ ] Monitoring/runbook ownership exists for critical flows.
- [ ] Docs, ADRs and source/content provenance are updated when needed.

## 16. Anti-patterns to actively avoid

- Treating route guards, hidden UI buttons or TypeScript types as security boundaries.
- Trusting a browser-supplied `userId`, owner ID, role or record permission.
- Assuming RLS is correct because app code includes `user_id = currentUser`.
- Using a service-role key for routine user operations that could use verified user context and RLS.
- Acknowledging outbox records before durable server confirmation.
- Returning `success: true` while silently ignoring part of a request.
- Storing duplicated copies of progress/evidence without a clear source of truth and conflict rule.
- Returning unbounded histories or `select *` from account endpoints.
- Adding Redis/Kafka/Kubernetes/microservices before measurement shows the need.
- Adding a CSP without testing dependencies, or weakening it broadly just to silence violations.
- Treating automated accessibility scans as proof of WCAG conformance.
- Retrying every failed request, including permanent 4xx errors.
- Logging tokens, passwords, cookies or full learner evidence to “help debug”.
- Treating a passing local SQLite test as proof of PostgreSQL RLS behavior.
- Claiming production readiness based on source code without checking live settings, hosting headers, backup restore or monitoring.
